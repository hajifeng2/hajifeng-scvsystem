# 02 - 评估框架（通用）

> 把筛选经验固化为标准维度 + 权重。**岗位特定项（加分词/风险词/红线/学历门槛）由岗位画像注入**，使框架跨岗位复用。
> 版本：v1.0

## 1. 维度与权重（100 分制）

| 维度 | 分值 | 核心问题 |
|:---|:---:|:---|
| D1 学历门槛 | 门槛 | 是否满足岗位学历/届次要求 |
| D2 项目积累 | 15 | 项目数与时间跨度 |
| D3 原创可信度 | 20 | 无 AI 代写/教程复刻自爆 |
| D4 岗位技术匹配 | 20 | 命中岗位刚需技能（加分词由画像定义） |
| D5 可验证性 | 10 | GitHub/视频/演示/上线 |
| D6 方向匹配 | 15 | 投递方向占比，无方向错配（风险词由画像定义） |
| D7 工程素养 | 10 | 版本控制/规范/质量意识 |
| D8 格式与逻辑 | 10 | 简历规范、逻辑清晰 |
| **合计** | **100** | |

> D1 为门槛项：不满足直接 C（拒），不再计分。

## 2. 各维度判定标准

### D1 学历门槛（门槛项）
- 满足岗位画像定义的学历/届次 -> 通过门槛
- 不满足 -> 直接 C

### D2 项目积累（15）
- ≥3 项目且跨度 ≥6 个月：15
- 2 项目或跨度 3-6 个月：8
- <2 项目或全为求职前 3 个月内临时补齐：0-3

### D3 原创可信度（20）-- 最高权重之一
- 全原创、描述具体：20
- 有"AI 辅助"但重点在"我做了什么"：12-15
- 出现"完全由 AI 构建""跟随教程复现"等自爆：0
- **AI 工作流标榜**（v1.2 新增）：简历把 AI Agent / Claude Code / Cursor / Codex / openspec / Vibe-Coding 当**核心亮点**描述（而非偶发工具），或实习内容为"搭建 AI 开发工作流"-> 扣至 5 分以下
- **撑底加分**（v1.2 新增）：候选人具备 C++/图形学(OpenGL/自研渲染器)/算法竞赛(蓝桥杯/CCF-CSP)/正规游戏公司实习等**自身底层功底**时，可抵消"偶发 AI 辅助"嫌疑，D3 不因偶发 AI 工具使用而扣分

### D4 岗位技术匹配（20）
- 命中岗位画像"必须命中"全部 + "加分命中"≥2：20
- 命中"必须命中"大部分：12
- 命中 ≤1 项：0-5
- **v1.2 细化（转正）**：从"命中关键词数"改为"是否解决具体技术问题 + 项目规模与技术栈是否匹配"。命中硬核词（帧同步/ECS/ILRuntime 等）但项目实为 Demo / 学习复刻 -> **不奖励**，配合 D3 扣分（孔祥健/阮仕钰案例）

### D5 可验证性（10）
- 多种可验证链接（GitHub + 视频/演示/上线）：10
- 单一链接：6
- 无链接：0
- **v1.2 收紧**：区分强/弱验证。**GitHub 代码仓库 = 强验证**；B 站 BV 号 / 优酷 / 百度网盘 / 私人视频 = **弱验证（6 分上限）**；Ludum Dare / GameJam 排名仅作参考、不单独计分（秦熙源案例：BV 号+LD 排名 ≠ 代码可验证）

### D6 方向匹配（15）
- 投递方向模块占比 ≥70%：15
- 50-70%：8
- <50%（方向错配）：0-3
- 占比 = 投递方向模块 / 全部项目模块；结合岗位画像定义的风险词频率判定

### D7 工程素养（10）
- 版本控制协作 + 规范习惯 + 质量意识：10
- 有版本控制但无质量意识：6
- 无版本控制经验：0-3

### D8 格式与逻辑（10）
- 结构清晰、无空洞描述：10
- 一般：6
- 术语堆砌/产品文案感：0-3

## 3. 红旗信号（命中即扣分或归零，覆盖其他加分）

### 3.1 AI 代写 / 包装过度
- **术语密度异常**：一段话 ≥3 个高级词汇且项目不复杂
- **"AI 辅助"当亮点**：写"代码完全由 AI 构建"= 自爆
- **AI 工作流标榜**（v1.2）：把 AI Agent / Claude Code / Cursor / Codex / openspec+claudecode / Vibe-Coding 当**核心亮点**写在技能栏或项目里，或实习内容是"搭建 AI 开发/Bug 修复工作流"--即使代码非纯 AI 生成，也按包装扣分（蒋志豪/孔祥健/秦熙源/苏添龙案例）
- **区分（v1.2.1 校准，Java 批次）**：① 技能栏列 AI 工具为**辅助** + 有扎实工程撑底（实习/具体优化数据/深度架构）= **不触发**（黄达熠：列 Cursor/Claude Code 但有浩鲸实习+single-flight/CAS 防超卖深度，Java 业务接受）；② **“造 AI 系统”**（用 Java/SpringBoot 自主实现 AI Agent/MCP/脚手架）= 撑底工程，不算 AI 代写（陈帅博 MiraAgent、刘欣远 AI Agent 脚手架，均业务接受）；③ AI 当项目**核心卖点** + 无自身深度 = 触发（客户端 6/11 淘汰）。判据关键看「自身技术深度」而非「是否提及 AI」
- **第三人称产品文案感**："彻底解决痛点""架构高度解耦""绝对精准""零 GC 分配"
- **技术栈与项目规模不匹配**：小项目堆高级架构词（8 容器微服务 / 46 通道事件总线 / 11Component+11System）
- **搜索词**：`AI生成 / AI Agent / AI工作流 / Claw / Copilot / Codex / Cursor / claudecode / openspec / Vibe-Coding / 复现 / 跟随教程`

### 3.2 教程复刻 / 零原创
- **项目名与热门教程重合**（培训市场泛滥的项目名）
- **出现"复现/复刻/跟随/学习/练手/拆解分析学习"**（v1.2 补"复刻/拆解分析学习"）
- **"学习+实现"句式**（"学习 XX 架构，实现了一套..."）= 学习项目，D3 扣分（孔祥健 ALSV4 学习 / 高佳罗跟随商业级教程完整复现）
- **技术描述像课程大纲**："实践了 XX 方案" = 照着做了一遍
- **多项目技术点雷同**（同套教程不同章节）
- **有仓库的看 commit 是否集中 1-2 周狂提交** = 赶工复刻

### 3.3 方向错配
- 岗位画像定义的**风险词频率 > 加分词频率** -> 方向不符

## 4. 评级阈值

| 总分 | 评级 | 处置 |
|:---:|:---:|:---|
| ≥80 | A | 推面试 |
| 65-79 | B | 电话初筛（验真伪） |
| 50-64 | C+ | 待定/备选 |
| <50 | C | 直接拒 |

## 5. 拒因分类（未通过者必填主因）

| 拒因 | 说明 |
|:---|:---|
| 方向错配 | 投递方向与简历重心不符 |
| AI代写 | 代码/成果由 AI 生成，自爆或露馅 |
| 教程复刻 | 项目为跟教程复现，原创性不足 |
| 积累太薄 | 项目数量/时间跨度不足 |
| 学校弱 | 学校层次低（**仅在其他条件相近时起作用，慎用为唯一拒因**） |

> 拒因分类可扩展。发现新拒因类型时回写本节并记入变更日志。
> 一人命中多个拒因时，取**主因**（最致命的那个），次因记 `reject_reason_secondary`。

## 6. 评估流程

1. 读候选人档案（`candidates/<姓名>.md`）
2. 逐维度打分，**每分附引用原文证据**
3. 检查红旗信号，命中则该维度扣分或归零
4. 汇总总分 -> 评级
5. 填回 frontmatter 的 `score` / `tier` / `reject_reason`
6. **写综合评估段**（评估卡第一节，见 `templates/单人评估卡模板.md`）：论述「合不合适 + 为什么 + 关键判断逻辑 + 短板 + 验证点」。不是条目罗列，是判断论证--读者看完即懂结论怎么来的，不用自己从打分表拼
7. 产出单人评估卡（综合评估 + 维度打分 + 红旗 + 优势/风险/建议）

> 综合评估是评估卡的「脸面」，放在打分表前面。飞书表 `评估详情` 列 = 综合评估精简版（~200 字），`核心原因总结` 列 = 综合评估的结论句（一句话）。

## 7. 降级规则（v1.1 待议，待多批验证后采纳）

- **D2 ≤5 时总分封顶 60（C+）**：防止"项目积累极薄但技术词多"被高估（源自客户端实习生批次的刘瑞案例）
- **D4 判定细化**：从"命中关键词数"改为"是否解决具体技术问题"（区分"堆名词"与"真解决问题"）

## 8. 迭代机制

每批分析结束后，若发现新的区分性特征或红旗信号，回写本文件：
- 新增维度（调整权重，保持总分 100）
- 补充红旗信号
- 校准阈值
- 在下方变更日志记录

## 9. 校准标签源（真实标签来源）

> Agent 自评不作为校准依据，统一用业务/Moka 真实标签校准。信号强度分层：

| 信号 | 含义 | 来源 | 强度 |
|:---|:---|:---|:---|
| **Moka 入职/待入职阶段** | 真录用（最强通过信号） | moka 待入职(3674)/入职阶段 | ★★★ definitive |
| **Moka 面试结论·通过** | 业务👍赞=通过 | moka `conclusions[].result` | ★★ pass |
| **飞书群 CheckMark** | 招聘者✓=通过 | 飞书招聘群反应（客户端群已用） | ★★ pass |
| Moka 面试结论·待定 | 未定 | moka `conclusions` | ★ 待定 |
| **Moka 面试结论·储备** | 人才储备库（弱通过/备选） | moka `conclusions`（测试岗 7-28 发现） | ★ 弱通过 |
| **Moka 面试结论·淘汰** | 业务👎向下=不通过 | moka `conclusions[].result` | ★★ fail |
| 飞书群无✓ | 未通过 | 飞书招聘群（无 CheckMark） | ★★ fail |

**校准流程**：用真实标签对照 Agent 评估结论，找分歧（Agent 评被接收但业务👎/未入职；或 Agent 评未通过但业务👍/入职），回写红旗/阈值/撑底判据。

**现状**：
- 飞书✓（客户端 16 人批）+ Moka 面试结论（通过/淘汰，7-12 简历库批）已用于 v1.2/v1.2.1 校准。
- **Moka 入职阶段数据待 Edge CDP 重抓**（本地 moka_output 无待入职阶段，停在 7-13/7-15）。入职信号是最强通过标签，重抓后用「入职者 Agent 是否评被接收」做最终校准。
- Moka 面试结论分布（本地）：客户端 通过4/淘汰7、Java 通过2/淘汰4、测试 通过7/淘汰9、策划 通过7/淘汰4。
